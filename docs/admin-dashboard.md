# 運営管理画面

## アクセス

本番環境では、次のURLから開きます。

`https://www.tateito-yokoito.jp/?admin=1`

管理者として登録されていないアカウントは、ログイン後もデータを閲覧できません。画面に表示される「ユーザーID」を使って、最初の管理者だけをSupabase SQL Editorから登録します。

```sql
insert into public.admin_users (user_id, role)
values ('画面に表示されたユーザーID', 'owner')
on conflict (user_id) do update
set role = 'owner', is_active = true;
```

登録後に管理画面を再読み込みします。

管理者ログインは、次のどちらの方法でも行えます。

- メールアドレスとパスワード
- メールで届く認証リンク

初めてパスワードを使う場合や忘れた場合は、管理者ログイン画面の「パスワードを設定・再設定」から設定メールを送信します。メール内のリンクを開き、新しいパスワードを登録してください。

## 権限

- `owner`: 管理者の追加・変更と整理モードを含む最上位権限
- `operator`: 日常運用担当者向けとして予約
- `viewer`: 閲覧専用として予約

管理画面は原則として閲覧専用です。非表示・復旧・アカウント退役は、`owner` が再認証して開始した期限付きの整理モードでだけ実行できます。`operator` と `viewer` は整理モードを開始できません。

## 確認できる内容

- 要対応: 招待メール失敗、文章生成失敗、決済途中、長期間止まっている初期登録
- 物語: 無料体験・購入状況、進捗、最終活動、語り・共有・サポーターの詳細
- アカウント: 氏名、メールアドレス、所有・お手伝い中の物語数、最終ログイン
- アカウント詳細: 関係する物語、アカウント単位の利用履歴・配信履歴
- 配信: 問い・サポーター招待・共有招待の送信先、状態、日時、エラー
- 決済: 決済状態、金額、Stripe Checkout ID、更新日時
- 語りを見る: 利用者向けの閲覧画面と同じ表示で、問い・原稿・写真を確認
- 本に仕上げる: 利用者向けの本づくり画面を閲覧専用で確認

## 整理モードと非表示ゾーン

通常時は非表示操作を出しません。`owner` が現在のパスワードまたは認証メールで再認証すると整理モードが始まり、「非表示ゾーン」と対象ごとの整理操作が表示されます。整理モードは初期設定で15分間有効です。画面を閉じてもサーバー側の期限を超えて操作はできません。途中で明示的に終了することもできます。

整理モードの有効時間はDB設定で変更できます。たとえば30分に変更する場合は、Supabase SQL Editorで次を実行します。アプリの再ビルドは不要です。

```sql
update public.admin_operation_settings
set integer_value = 30, updated_at = now()
where setting_key = 'organization_mode_minutes';
```

### 物語の非表示

物語を非表示にすると、通常一覧・検索・集計・配信履歴から除外されます。回答、音声、写真、購入情報は削除しません。整理モードの非表示ゾーンでは内容を確認でき、「表示中に戻す」で復旧できます。

### アカウントの退役

アカウントを退役させると、通常の管理画面から非表示にしたうえでログインを停止し、Supabase Authとプロフィールのメールアドレスを重複しない内部用アドレスへ変更します。元のメールアドレスは新規登録で再利用できるようになります。所有・購入・参加している物語は自動では非表示にせず、元データも削除しません。稼働中の管理者アカウントは退役できません。

退役前のメールアドレスはRLSで一般公開されない退役台帳に保持します。元のメールが未使用なら復旧できます。元のメールが新しいアカウントで使用中の場合、そのアカウントを上書き・統合せず、別の未使用メールを指定した場合だけ古いアカウントを復旧します。

以前の最小版で「非表示だけ」にしたアカウントは、非表示ゾーンでその状態を区別して表示します。そのまま表示中へ戻すか、改めて退役してメールを解放できます。

完全削除と自動パージは行いません。

管理画面へのアクセスは `admin_audit_logs` に記録されます。

「語りを見る」と「本に仕上げる」は、管理画面専用に複製した画面ではありません。利用者画面と同じReactコンポーネントを再利用し、管理画面から開いた場合だけ編集・写真追加・収録変更を無効にします。利用者画面の表示を更新すると、管理者プレビューにも同じ変更が反映されます。

プロジェクト詳細には旧仕様の語り一覧を重ねて表示せず、「語りを見る」を唯一の閲覧導線とします。管理画面では「物語の主体」「利用アカウント」「購入者」を別の役割として明示します。物語の主体と利用アカウントの氏名が同一でも省略せず、どちらの情報かが分かる表示にします。

購入情報は物語の主体や現在の所有者とは分けて扱います。決済時点の購入者アカウントを物語に固定保存し、物語詳細では購入日と購入者を併記します。購入者名はアカウント詳細へのリンクです。購入記録がない無料体験・既存利用・ギフト利用では購入者を表示しません。

購入者の氏名とメールアドレスは注文時点のスナップショットとして注文に保存します。後でアカウントの登録氏名を変更しても、過去の注文履歴の購入者表示は変更しません。

プロフィールの「アカウントの登録氏名」は通常は読み取り専用です。「変更する」を選んだ場合だけ姓・名を編集でき、変更前後を確認してから保存します。ここで変更するのは利用アカウントのプロフィールだけで、紐づく物語の主体名は変更しません。旧データで姓・名が未登録の場合も、既存の表示名を自動分割・自動保存しません。

氏名は `get_admin_project_display_names` で人物の姓・名、人物の表示名、所有者プロフィールの姓・名の順に解決します。

## 履歴の単位

利用履歴は二重保存せず、1件のイベントに `subject_user_id` と `book_project_id` を持たせます。同じイベントをアカウント詳細では「その人の利用」、物語詳細では「その物語の進行」として表示します。

- アカウント単位: 登録、アプリを開いた、配信設定変更、所有・参加している物語での操作
- 物語単位: 物語作成、問いを開いた、回答保存・更新、回答完了・スキップ
- 配信単位: 配信予定、送信、到達、開封、回答、失敗、取消

回答本文、文字起こし、音声・写真の内容は履歴の `metadata` に複製しません。

## 要対応の単位

要対応の一覧は物語単位でまとめます。招待送信失敗、問いの配信失敗、文章生成失敗、決済確認停止、無料体験停止を対象にし、同じ物語で複数の問題が起きた場合は詳細画面に個別の対応項目を並べます。

問いの配信失敗は `question_delivery_logs` の履歴を変更せず、`admin_attention_items` に運営上の未解決・解決状態を別保存します。物語詳細を開いただけでは解決になりません。管理者は次のどちらかで完了させます。

- 「再送する」: 元と同じチャネルへ新しい配信試行を作成し、成功した場合は元の要対応を自動解決
- 「対応済みにする」: 「システムを修正した」「別の方法で連絡した」「対応不要と判断した」から理由を選び、必要ならメモを残して解決

後日別の配信が失敗した場合は、解決済みの項目を再利用せず、新しい要対応として記録します。

## 配信状態

`question_delivery_logs` は問いの配信ライフサイクルを記録します。メール事業者が要求を受け付けた状態を「送信済み」、Webhookで到達を確認した状態を「到達」として区別します。実際の問い配信処理・Webhookはこのテーブルを更新し、宛先アカウントと対象物語を必ず両方記録します。

問いは登録メールアドレスへ必ず配信し、利用者が希望した場合だけ認証済み携帯電話番号へSMSも追加配信します。電話番号は6桁のコードで本人確認し、初回の配信設定とホームの「問いの届け方」で追加・停止・再開・変更できます。メールとSMSは同じ問いURLを共有しますが、配信履歴はチャネル別に記録します。
