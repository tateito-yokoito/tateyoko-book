## 無料相談と一括決済

通常制作: 商品・追加冊子選択 → サーバー見積 → Stripe → 注文確定 → 既存制作オンボーディング。

聞き取り制作サポート: 商品（standard/premium/相談して決めたい）・追加冊子・連絡先・相談内容を無料の `consultation` として保存。相談段階では有料 `commerce_order` を作らず、制作権限も付与しない。スタッフが確認し、電話またはメールで内容・日程を調整する。商品未決定の場合は合意後に選択を確定する。決済前にサーバーで最新価格・割引・内容を再見積し、申込時から変わった場合は購入者に再確認を求める。合意済み見積から一回限りの決済案内を作成し、基本商品＋追加冊子＋20,000円を一括決済する。Webhook/復帰同期で支払済み注文を相談申込へ一度だけ紐付ける。決済失敗・中断では相談を維持し、制作は開始しない。

相談の状態候補: `submitted` → `in_review` → `agreed` → `checkout_pending` → `paid` → `in_production` → `completed`。`cancelled` を別終端とし、支払済み判定は決済確定済み注文への参照に基づける。通知失敗やWebhook再送で重複注文を生じさせないため、相談IDと決済案内IDに一意制約を置く。フォームの閲覧は本人/申込者と権限を持つスタッフのみに限定する。スパム・連投制限、個人情報保持期間、通知先は既存運用と照合する。

## 購入後の進行先

装丁と制作方法は別属性として保持する。通常制作のstandard/premiumは現行の制作ルートへ進めるが、完成時の表紙・発注・発送に装丁を引き継ぐ。サポート付き注文は決済後・再ログイン・リロード後も「申込完了／スタッフからの連絡待ち」へ進め、通常録音オンボーディングを自動開始しない。家族ギフトは受取・制作主体の現行分離を維持する。スタッフへの制作権限は購入だけで自動付与せず、本人同意・担当者の認証・最小権限・操作記録を条件にする。家族サポーター権限をスタッフ用に流用しない。

## 決済整合性と移行順序

1. 適用済みDB/本番Edge Functions/元checkoutの差分を読み取り照合し、テスト可能な移行基準を固定する。
2. 新商品マスタ・注文明細・相談状態を後方互換の追加移行として用意する。旧コード・旧Stripe価格IDは変更しない。
3. サーバー共通見積を実装。割引キャンペーンの対象範囲は既存ルールを維持し、standard/premiumへの対応関係を明示的に決める。見積・注文・Stripe line itemの総額一致を確認する。
4. 新Stripe価格IDはテスト環境で別途用意。価格IDと通貨・金額・税区分をStripeから検証し、古いIDを金額変更後に再利用しない。
5. Checkout・Webhook・復帰同期を冪等化し、購入後ルートとスタッフ一覧を実装する。
6. 旧注文と新注文を併存させてテストする。HPの変更は別Phaseで比較プレビュー承認後に行う。

本番DB、本番Stripe、決済の停止/再開、本番デプロイはそれぞれ実行前に承認を得る。現行 `EXPERIENCE_CHECKOUT_ENABLED` は停止ゲートとして流用可能だが、変更は承認後に行う。
