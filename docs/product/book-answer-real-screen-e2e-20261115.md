TESTでは初回音声文字起こしが403になり、既存の `20261104000200_project_role_links.sql` と `20261111000100_helper_private_media_boundaries.sql` から `is_project_co_manager` と `book_role_is_helper` の定義のみ追加した。その後、音声正式保存が `ON CONFLICT` の複合キー欠落で停止したため、既存の `20261104000400_scope_questions_and_answers_to_project.sql` と同じ `answers_project_user_sequence_unique` インデックスをTESTに追加した。いずれもTESTの欠落を埋めたもので、今回のアプリ変更に伴う新規DB migrationではない。ほかの権限関数・RLS・Storageが本番相当になったという証明でもない。本番DBは変更していない。

追加のTEST DB確認では、`answers`・`book_projects`・`media_assets`・`seasonal_memory_records`・`user_questions` のRLS有効化、写真・音声Storageバケットの非公開設定、回答の `(book_project_id,user_id,sequence_order)` 一意インデックス、必要な役割判定関数を確認した。これは権限別の実アクセス結果や本番との完全一致を示すものではない。TESTの既存Storageポリシーには広範な条件を持つものもあるため、直接アクセス境界の再検証を要する。

Storage直接アクセスの追加確認：同じ架空写真・音声の匿名公開URLは両方HTTP 400。TEST DBで `authenticated` ロールとJWT `sub` を模擬し、対象の非公開Storageオブジェクト2件をSELECTしたところ、所有者は2件、無関係の架空ユーザーは0件だった。所有者の正の対照を含むRLS確認である。ただし、別ユーザーの実JWTを使ったStorage APIの直接GET・署名URL発行までは未実施。

実PDFの再試験には、TEST専用Cloud Runレンダラーを現在の `src/lib/bookEdition.js` を含むイメージへ更新する必要がある。ローカル環境には `gcloud` がなく、TESTレンダラーの更新は実施していない。Edge・DB・本番レンダラーは変更していない。

参考として、現行リポジトリの組版スクリプトに架空の写真1枚・本文なし・質問ありの版データを渡すと、例外なくB5相当の8ページPDF（128,201 bytes）をローカル生成した。ただし写真URLを `file://` にしたため、HTMLレンダラーのHTTPS限定条件で画像は掲載されなかった。ページ画像を目視確認済み。この診断結果は写真入りPDFの合格証跡ではない。TESTレンダラーの旧版差分が解消するまでPDF項目は失敗のままとする。
