# 利用動線マスター

## 正本

利用動線、利用者の役割、状態遷移、分岐条件、設定・同意の意思決定時点は、[`user-flow-master.xlsx`](./user-flow-master.xlsx) を正本とする。

対象は、HPの入口から無料3問、購入、本人Accountへの接続、はじまりの章、本編、仕上げ、完成後まで。

## Person中心の原則

- Personは「誰の人生・作品か」を表す主体、Accountは操作・認証・認可の主体として分ける。
- 同じPerson／Projectは、本人Account、Supporter Account、または両方から操作できる。
- 上位の進め方は「本人が進める」「サポーターにおまかせする」の2つとする。これは主な操作Account・端末を表し、固定コースにはしない。
- ユーザー向けUIでは「サポーターにおまかせする」を「家族・信頼する方におまかせする」と表現する候補を基本とする。
- 共同利用は独立した進め方にしない。「本人が進める」にSupporterを追加してもよく、「サポーターにおまかせする」に本人Accountを後から接続してもよい。
- 「サポーターにおまかせする」では本人Accountや本人端末を必須にしない。本人の了承と意向を確認したSupporterが、語りの整理、写真、共有設定、本編開始、仕上げ、製本注文等を代理操作できる。
- 本人Accountは後から任意で既存Personへ接続できる。接続時に新しいPersonやProjectを作らない。
- PayerはPerson・Account・操作者とは独立して記録する。
- Supporterは、本人が信頼し、語りや作品づくりを手伝ってもらう制作メンバーとする。家族に限定せず、友人、仕事仲間、施設スタッフ等もなり得る。
- Supporterとして明示的に参加した人は、制作のため、原則として全語り、音声、写真、下書き、進捗、ブック制作等へアクセスできる。細かな閲覧Permissionをユーザーに選ばせない。
- Family / ViewerはSupporterと分ける。家族一般やViewerが見られるのは、家族共有した語りと、共有されたWebブック・完成作品だけとする。制作途中の全記録へ自動的にアクセスさせない。
- 語りの「自分だけ」という表現は避け、「家族に共有しない」または「制作中は非公開」と表現する。Supporterには制作のため表示されることを、参加時に一度説明する。
- Supporterには `personal` と `staff` の区分を設ける。`staff` は縦糸横糸スタッフによる制作サポート向けで、担当期間、操作・閲覧ログ、担当終了時のアクセス停止を別途管理する。
- 進め方とSupporterの追加・停止は開始後も変更できる。
- 本人Accountの有無と通知先は進め方に固定しない。通知先は本人、Supporter、双方を将来設定可能な構造とする。

ケースの位置づけは次のとおり。

- A：本人起点
- B：家族起点
- C：Bの受取人側ビュー。独立した契約フローではなく、招待された本人から見た体験確認に使う。

## 制作サポートの試験提供

- 家族や友人等に制作を頼める人がいない利用者へ、縦糸横糸スタッフによる制作サポートを少人数で試験提供できる。
- 利用者からは「サポートを希望する」として希望を受け付ける。申込ではなく希望受付とし、運営が状況を確認してから対応可否を案内する。
- 希望送信時点では利用確定としない。対応容量を超える場合は新規受付を一時停止できる。
- 価格、提供回数、1回あたりの時間、SLAはまだ商品条件として固定しない。初期運用では目安を内部管理し、利用者へ一律に約束しない。
- 希望受付、調整中、対応中、終了の状態と、支援内容、作業時間、利用者が止まった箇所を記録する。商品化とプロダクト改善の判断材料にする。
- 対応開始時に運営が `staff` Supporterを設定し、担当終了時にアクセスを停止する。

## 他の正本との関係

- 商品・ブランド・UXの原則は [`../../product-brand-ux-master-v2.0.md`](../../product-brand-ux-master-v2.0.md) を優先する。
- 認証、権限、個人情報保護、DB制約、RLS、決済の技術的安全条件は、承認済みの実装仕様、migration、コードをExcelだけで上書きしない。
- Excelの「実装状態」は、記載された根拠の範囲を示す。本番反映やE2E完了を自動的に意味しない。

正本間に矛盾を発見した場合は、どれかに勝手に合わせない。`04_運営チェック` に論点、影響、確認先、次アクションを追加し、判断後に関係する正本を更新する。

## 更新方法

1. 会話やレビューで論点を整理する。
2. 決定した内容を同じ `user-flow-master.xlsx` へ反映する。
3. 進め方、SupporterとFamily / Viewerの区別、Account、操作者、語る人、Person、Payer、Deviceの関係が崩れていないか確認する。
4. 設定や同意を変更した場合は、`02_設定同意` と `05_実装対応` も確認する。
5. 未確認の保存先や実装状態は推測せず、`要確認` として残す。
6. Excelと関係する正本だけを対象にコミットする。

`user-flow-master-v0.2.xlsx` のような別バージョンファイルは作らない。履歴と変更理由はGitで管理する。

## 構造の固定

2026年9月21日時点で、シート構成、主要列、Flow ID体系を一旦固定する。以後は商品仕様の意思決定と、実装差分の更新を中心に行う。

同日、上位概念を「2つの進め方＋制作Supporter＋Family / Viewer」へ更新した。本人Accountなしでも完結できるPerson中心の原則を保ちつつ、Supporterには制作内部への原則フルアクセスを付与し、家族一般への共有とは分離する。`01_利用動線` の進め方列と `06_支援スタイル・権限` は、この承認済み変更を反映したものとして扱う。

新しい運用上の必要が確認できた場合を除き、列やシートを追加して構造を磨き続けない。構造変更が必要な場合は、先に `04_運営チェック` へ理由と影響範囲を追加する。

## 実装時の扱い

Codexや実装担当者は、利用動線を変更する前にこのExcelを確認する。既存コードと異なる場合、コードへ自動的に合わせず、仕様差分として確認する。

ただし、Excelに記載がないことを理由に認証・権限・プライバシーの既存ガードを弱めてはならない。

### 制作Supporterの認可・了承境界

- `production_mode` は主な進め方だけを表す。制作アクセスや本編開始の権限は、明示的なSupporter関係と有効な `family_production_consents` を根拠とし、進め方の選択だけでは付与・取消しない。本編開始時の本人意向の確認は別途必要とする。
- 既存Supporterが本人の意向を確認したと自己申告することを許容する。これは本人認証ではない。確認したactor・日時・対象Person／Project・Supporter関係を監査可能にする。
- 本人Accountを後付けしても同じPersonへ接続し、本人から制作支援を停止できる。一度本人が停止した後、Supporterの自己申告だけでは再有効化できない。

事前照合の証跡・本番移行条件は [`production-supporter-preflight.md`](./production-supporter-preflight.md) を参照する。

既存本人Account・購入済みProjectに登録済みのSupporterを制作支援へ移行する手順は
[`existing-supporter-adoption-runbook.md`](./existing-supporter-adoption-runbook.md) を参照する。
新規の本人Accountなしフローとは別に検証し、既存の本人関係・契約・共有を保持する。
SupporterとしてのAccount登録や母の語りの操作を、Supporter自身の物語開始・無料3問の実施履歴として扱わない。
