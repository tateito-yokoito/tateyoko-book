# 「本に仕上げる」紙面ビューワー仕様案

2026-10-21。対象は編集中の冊子紙面と注文後の校正紙面。縦糸+横糸Webブックの閲覧UI、印刷用PDFのページ構造は変更しない。

実装状況：TESTアプリに全画面ビューワーを配置。紙面HTMLの各ページを表示し、画面幅に応じて見開き／単ページ、前後ボタン・矢印キー、スマホの横スワイプ、拡大ボタンに対応した。Safariで当初の`srcDoc`内スクリプトが実行されず白紙になったため、スクリプト不要のページ別表示に変更して実画面で表示と送りを確認した。Cloud Runステージング生成器を更新し、TESTのB5・8ページ校正PDFと見開きp.2–3・p.4–5を照合した。本文を読む補助表示、ピンチ・ダブルタップ拡大、目次ジャンプ、100ページ規模の実機検証は今後の品質改善として残る。

## 基本方針

- 紙面は既存の `buildBookPages` を唯一のページ順・内容の決定元とする。ビューワーは表示方法だけを変え、B5紙面の文字サイズ、改ページ、写真位置を勝手に変えない。PDFと同じページ番号・白紙を見せる。
- 「紙面プレビュー」を開くと、PCでは画面幅を使った専用の見開き、スマートフォンでは1ページずつ横スライドを表示する。現行の最大760pxの編集画面内に見開きを押し込まず、全画面オーバーレイをポータル等で画面全体に出す。
- 表紙プレビューは本文PDFの1ページ目ではない。初版のビューワーは本文の扉（p.1）から始める。将来、表紙・裏表紙も同じ閲覧体験に追加するときは、印刷本文のページ番号に混ぜず「表紙」と表示する。

## PCの見開き

- 最初は扉のp.1を右側に1ページで見せる。次は左p.2・右p.3、その次は左p.4・右p.5、と物理的な本の順で進む。最後に片側がない場合は空の台紙を見せ、PDFに存在しないページ番号を作らない。
- 画面に十分な幅があるときだけ見開きにする。2ページの文字が小さくなりすぎる幅では、PCでも単ページ表示へ切り替える。ウィンドウのリサイズ時は同じページを中心に保つ。
- 前後ボタン、左右矢印キー、クリックまたはトラックパッドの横操作で1見開きずつ移動する。ページ番号、総ページ数、現在の語り名、目次からの移動を用意する。自動めくりはしない。
- めくりは250～400ms程度の紙の影・回転を伴う控えめな演出とし、文字が読める状態を維持する。操作を連打しても順番が飛んだり、途中のページが重なったままになったりしない。動きを減らすOS設定では演出を省き、即時に切り替える。

## スマートフォン

- 1画面に1ページ。左右スワイプと前後ボタンで移動し、スワイプ後は必ずページ端に収まる。縦スクロールは画面全体の意図しないページ移動に使わない。
- B5紙面を横幅に収めると本文16ptでも小さく見えるため、ダブルタップ・ピンチまたは拡大ボタンで紙面を拡大し、拡大中はページ内のパンを優先する。拡大を戻すと再び横スワイプでページ移動できる。
- 長文を読むための「本文を読む」表示も併設する方向とする。これは画面幅に合わせて文字を再配置する閲覧補助であり、校正用のページ位置を確認する「紙面を見る」と明確に区別する。初版で間に合わない場合も、拡大操作と実機での可読性確認を必須にする。

## 編集との連動と実装境界

- 収録・順序・写真・文章を変えたら、既存の紙面モデルを更新して開いているビューワーに反映する。再描画しても先頭へ戻さず、語りIDとその中の位置を基準に現在の場所を保つ。対象の語りを外した場合は、次の収録語りか近いページへ移動する。
- PDF生成ボタンは現行どおり明示操作時だけ呼ぶ。ページめくりやズームでCloud RunやSupabaseのPDF生成を起動しない。
- 現行の `renderBookPrintHtml` のページ内容と印刷CSSを共用し、画面専用の表示層を分ける。`srcDoc` を丸ごと差し替えるたびに閲覧位置が失われる構成は避ける。本文を画像化して全ページ常時読み込む方式も避ける。
- 表示中の見開きと前後1見開き程度だけを描画し、写真は必要な分を先読みする。署名URLの期限切れ時は再発行し、ページを開けない理由を画面へ出す。

## 検証・採用判断

1. 架空の8ページと旧サンプル規模の約100ページで、p.1単独、p.2–3の見開き、写真ページ、写真なしの同一ページ内の質問＋本文、末尾の白紙を確認する。
2. 表示ページ数・順番・本文・写真がPDFと一致し、語りの並べ替えや写真追加の直後も現在位置が保たれることを確かめる。
3. PCのマウス・トラックパッド・キーボード、iPhone/Androidのスワイプ・拡大、画面回転を実機で確認する。スクリーンリーダーでは現在ページを告知し、隠れたページへフォーカスが入らないようにする。
4. 3Dページめくりライブラリは見開きの試作で比較する。DOMの文字を鮮明に保てること、100ページ規模で隣接ページだけを扱えること、編集中の更新とアクセシビリティを阻害しないことを採用条件にする。条件を満たさなければ軽いCSS演出を使う。

仕様上の優先順は「PDFとの一致と可読性 → 操作の確実さ → めくり演出」。見た目のために印刷用のページ構造を変えない。

参考：[StPageFlip（HTMLページ対応のめくり演出候補）](https://github.com/Nodlik/StPageFlip)、[MDN CSS Scroll Snap](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap)、[W3C WAI カルーセルのアクセシビリティ](https://www.w3.org/WAI/tutorials/carousels/)。採用前に実アプリの編集追随と実機で比較する。
