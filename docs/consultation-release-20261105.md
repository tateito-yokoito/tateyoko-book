# 事前相談APIの本番公開手順（準備のみ）

## 差分

- 本番の `commerce_v2_consultations` は既存列のみ。TESTには控えメール・運営通知の状態を記録する4列と2制約がある。
- 本番の `submit-commerce-v2-consultation` は受付保存のみ。TEST版は受付番号を返し、希望者だけに回答控えを送り、希望の有無にかかわらず運営通知を送る。
- 本番の既存受付行は保持する。新列は既定値で追加し、既存の相談本文・連絡先・日時は更新しない。

## 承認後の適用順

1. 本番のバックアップ状態、相談件数・現行列・関数バージョンを記録する。`CONSULTATION_IP_HASH_SECRET` と `RESEND_API_KEY` が設定済みで、送信元ドメインが有効であることを値を表示せず確認する。
2. `supabase/migrations/20261105010000_commerce_v2_consultation_receipts.sql` の1件だけを適用する。4列と2制約、既存行の件数・主要値を照合する。
3. `submit-commerce-v2-consultation` だけをこのブランチのソースで更新する。現行バージョン5の定義は復旧用に保持する。
4. 架空の相談内容で1件だけ受付を行う。受付番号、DB保存、任意の控えメール、運営通知、管理画面からの閲覧を確認する。実際の相談と区別できる名前・本文を使用する。

## 異常時

- まずフォームの公開を停止する。受付関数を保存済みの本番バージョン5へ戻す。追加列は既存行を守るため残し、削除しない。
- メールだけが失敗した場合、受付は取り消さない。DBの `admin_notification_status` / `customer_email_status` と管理画面の「事前相談」で受付記録を確認し、運営側で個別対応する。
- 本番API・DB・main・Vercel・Stripe・公開フラグ・決済スイッチの変更は最終承認後に限る。

## 公開順序

1. HP候補 `94c3807` を最新mainへ統合し、`/support-consultation/` と35,000円／65,000円、聞き取り制作サポート＋20,000円、無料3問・本人購入・ギフトA/Bの入口を確認する。
2. PR #28を最新mainへ接合する。共通購入画面の「スタッフに聞き取ってもらう」からフォームへ遷移できることを本人・ギフト両方で確認する。
3. 相談APIの上記DB・関数差分を承認後に適用する。
4. 合意済みの順序で `VITE_GUEST_TRIAL_ENABLED=true`、`VITE_COMMERCE_V2_ENABLED=true`、Vercel再デプロイ、表示・入口確認、最後に `COMMERCE_V2_CHECKOUT_ENABLED=true` を実施する。異常時は新決済スイッチを最初に停止する。
