# 事前相談APIの本番適用結果と公開手順

## 適用結果（2026-11-06 JST）

- 承認に基づき、本番DBの4列・2制約を適用し、受付関数をバージョン5から6へ更新した。既存受付1件は保持された。
- 架空の受付4件を保存。控え希望なしでは控えメールを送らず、希望ありでは受付番号・日時・回答本文を含む控えを送信した。運営通知も受信確認済み。
- 同期的な控えメール送信失敗時も受付を保持し、`customer_email_status = 'failed'` を記録した。
- DB変更はSupabaseの移行として適用した。リポジトリ内のSQLは、別の履歴経路から再実行されても重複制約を作らない。
- HP候補、PR #28、公開フラグ、決済スイッチは未変更。

## 差分

- 本番の `commerce_v2_consultations` は既存列のみ。TESTには控えメール・運営通知の状態を記録する4列と2制約がある。
- 本番の `submit-commerce-v2-consultation` は受付保存のみ。TEST版は受付番号を返し、希望者だけに回答控えを送り、希望の有無にかかわらず運営通知を送る。
- 本番の既存受付行は保持する。新列は既定値で追加し、既存の相談本文・連絡先・日時は更新しない。

## 実施した適用順

1. 本番のバックアップ状態、相談件数・現行列・関数バージョンを記録した。必要なシークレットと送信元は、実際の受付・送信で有効性を確認した。
2. `supabase/migrations/20261105010000_commerce_v2_consultation_receipts.sql` と同内容の1件だけを適用した。4列・2制約と既存行1件の保持を照合した。
3. `submit-commerce-v2-consultation` だけをこのブランチのソースで更新した。旧バージョン5の定義は復旧用に保持した。
4. 実際の相談と区別できる架空データで受付、受付番号、DB保存、控えメール、運営通知、失敗時の保持を確認した。

## 異常時

- まずフォームの公開を停止する。受付関数を保存済みの本番バージョン5へ戻す。追加列は既存行を守るため残し、削除しない。
- メールだけが失敗した場合、受付は取り消さない。DBの `admin_notification_status` / `customer_email_status` と管理画面の「事前相談」で受付記録を確認し、運営側で個別対応する。
- HP・PR #28のmain統合、Vercel・Stripe・公開フラグ・決済スイッチの変更は別途承認後に限る。

## 公開順序

1. 相談APIの上記DB・関数差分は適用・確認済み。新フォームを先に公開しない順序を守った。
2. HP候補 `94c3807` を最新mainへ統合し、`/support-consultation/` と35,000円／65,000円、聞き取り制作サポート＋20,000円、無料3問・本人購入・ギフトA/Bの入口を確認する。
3. PR #28を最新mainへ接合する。共通購入画面の「スタッフに聞き取ってもらう」からフォームへ遷移できることを本人・ギフト両方で確認する。
4. 合意済みの順序で `VITE_GUEST_TRIAL_ENABLED=true`、`VITE_COMMERCE_V2_ENABLED=true`、Vercel再デプロイ、表示・入口確認、最後に `COMMERCE_V2_CHECKOUT_ENABLED=true` を実施する。異常時は新決済スイッチを最初に停止する。
