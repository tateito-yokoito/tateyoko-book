# BOOK完成後の運営確認：配置と復旧

## 対象

顧客が新たに完成確定したBOOKだけを運営確認へ送る。既存の公開済みWebブックと既存の制作ジョブにはケースを作らず、URL・版・注文を変更しない。印刷会社への発注と発送は手動。

## 本番配置順（別途承認後）

1. 本番DBのバックアップ、既存制作ジョブ・公開版の件数、関数定義とStorage設定を保存する。`20261108010000_book_ops_review.sql` だけを適用し、`book_ops_rollout.enabled=false` を照合する。この段階では従来の公開処理が続く。
2. `publish-voice-edition`、`book-production-worker`、`book-production-status` を現在の**本番配置版**からの差分として更新する。新規 `book-ops` を配置する。Worker の `BOOK_RENDER_URL`、`BOOK_RENDER_SECRET`、`RESEND_API_KEY` と運営通知先 `OPS_ALERT_EMAIL`（または `ops_monitor_settings.alert_email`）を値を表示せず確認する。送信先がなければ確認待ち一覧には残るがメール通知は届かない。
3. 管理画面を含むアプリを配置し、旧作品の閲覧・制作再開・既存ジョブの公開を最小限確認する。新しい確認待ち一覧・校正PDF・非公開Web案へのアクセスを運営権限で確認する。
4. すべて正常な場合に限り `update public.book_ops_rollout set enabled=true, enabled_at=now() where id=true;` とする。以後に作られたジョブだけが運営確認待ちとなる。最初の1件について原本 v0、PDF/Web版ID、通知、承認前非公開を確認する。

## 運用

「完成作品」で確認待ちを開き、校正PDFとWeb案の本文・音声・写真・動画、注文・配送先を照合する。修正は理由付きの別版に保存し、再生成されたPDF/Web案の版IDが一致するまで承認しない。人名・日付・意味、写真の削除や差し替えなどはメール等で顧客に手動確認し、依頼日・回答日・承認内容を記録する。最終承認後だけWebを公開する。

入稿用PDFは校正PDFと別扱い。印刷会社の用紙寸法、塗り足し、裁ち落とし、解像度、色空間、フォント埋め込み、ページ順、QR読み取り、ファイル命名・納品方法、再入稿条件が未確定。仕様確認後、承認済み版から別途作成した入稿用PDFを運営がアップロードし、仕様確認記録・版確認・配送先確認を済ませて「入稿準備完了」とする。以降の発注・印刷・発送・納品は運営が手動更新する。自動入稿はしない。

## 異常時

新規案件の自動公開・プレビュー・版の不一致などが起きたら `book_ops_rollout.enabled=false` に戻し、新しい完成確定の受付を一時停止して案件を特定する。既存の原本・修正版・公開済みWebブックは削除しない。誤公開は該当Web版だけ非公開へ戻し、原因を調べる。アプリ/Edge は保存済みの直前版へ戻せるが、DBの新テーブルや履歴を即時削除しない。DB関数の復旧は保存済み定義を使い、公開状態と各版IDを照合してから再開する。メール通知失敗時は確認待ち一覧から手動対応する。
