# 顧客ごとのブック・Webブック同時制作：仕様と進め方（案）

2026-10-19。4色スタンダード冊子とプレミアム上製本のサンプル発注を踏まえた実装案。これは今後の制作仕様であり、現行アプリですべて実装済みという意味ではない。

## 目的と原則

本人の語りを文字起こし・編集し、**「本に仕上げる」では現在の紙面を常に見られる**ようにする。注文が成立した時点の作品データを固定し、そこから入稿用PDFと対応するWebブックを生成する。編集中の細かな変更を完成Webブックへ逐次反映しない。紙とWebで語りの順番、文章、写真・キャプション、音声との対応が食い違わないことを最優先する。スタンダードとプレミアムは同じ作品を使う場合、本文・Webブックの版を共有し、装丁と印刷条件だけを別の出力設定にする。

録音・動画や文字起こしの原本は「わたしの語り」に残す。作品に使う文章は、話者の意味を変えずに読みやすく整えた編集版を選べるようにし、原文との差分と編集履歴を保持する。質問番号と音声ファイル名の一致を前提にしない。音声・写真は安定した素材IDで語りに結び付ける。音声のない語りも本文と写真だけで成立させる。

## 一つの作品データ

編集中は現在の選択・編集状態から**下書きの紙面モデル**を計算する。注文が成立したら、既存の `book_work_manifests.snapshot` を作品確定の起点にする。ただし印刷工程が使えるよう、下記を明示的に正規化した「制作マニフェスト」を別途生成する。これは一作品の特定版を示し、再生成しても同じ結果になる入力である。

| 項目 | 必要な内容 |
| --- | --- |
| 作品識別 | 作品ID、版ID、スキーマ版、入力データのハッシュ、確定日時、確認者 |
| 表紙 | タイトル、サブタイトル、著者表示、日付等の任意表示、写真とトリミング、選択した装丁 |
| 収録 | 章と語りの順番・見出し・本文・質問の表示有無。語りIDとメディアIDは保持する |
| 写真・声・動画 | 各語りに対応する素材ID、表示順、キャプション、使用可否、保存版の素材ハッシュ。動画はWeb向けに保持する |
| 共有 | 家族共有とQRによる閲覧を別々に確定した結果。紙へのQR掲載可否 |
| 出力 | 用紙・仕上がり寸法・塗り足し・綴じ方・ページ数・印刷色・背幅・印刷会社テンプレート版 |

紙面とWeb表示はこの確定版のみを読む。生成途中で更新される `answers` や元のStorageを再読込しない。原本を直しても完成版に無断反映せず、改訂版を明示的に作る。既存の `confirm_book_work` が確定後の更新を拒むため、将来の改訂・増刷には版を増やす設計が必要である。単に既存行を上書きしない。

## 顧客と運営の制作フロー

1. **素材を整える**：録音・動画の保存、文字起こし、読みやすい文章への編集、写真の選択とキャプション入力を行う。生成AIによる整文は下書き扱いとし、語り手の意図・固有名詞・年代・人物名を本人または許可された支援者が確認する。
2. **本に仕上げる**：収録/非収録、語りの順番、章、見出し、文章、写真の追加・差し替え・並べ替え、表紙の変更を保存するたびに、開いている紙面イメージを自動更新する。別画面へ見に行く操作を求めない。重い組版は短い待機を挟んで非同期に再計算し、編集中の反応を止めない。Webブックはこの段階では生成しない。
3. **その時点のPDFを受け取る**：「現在の紙面をPDFでダウンロード」ボタンから、押した時点の編集状態を固定してPDFを書き出す。下書きであることをファイル名とPDF上の明瞭な表示で示し、入稿用最終版や公開Webブックの完成と混同させない。画面の紙面イメージとPDFは同じ組版定義から作る。
4. **注文前に内容を確認する**：本人が全文、写真・キャプション、音声・動画との対応、表紙表記、家族共有、QR閲覧を別々に確認する。QR公開は購入や家族共有から自動的にONにしない。QRを載せる場合は、リンクを知る人が閲覧できることを明示する。注文開始時に承認した編集状態を「注文待ちスナップショット」として保存し、決済中の編集は一時停止する。他端末からの変更にも版番号で競合を検出する。
5. **注文成立時に作品版を固定する**：サーバーで注文成立を確認した後、注文待ちスナップショットを制作マニフェストとして固定し、使用素材をコピーする。決済画面を開いた時点やブラウザーで「完了」が表示されただけでは確定しない。無料注文も同じサーバー側の注文成立イベントで扱う。決済失敗・離脱時は完成版やWebブックを作らず、注文待ち状態を解除して編集へ戻れる。
6. **注文完了後にWebブックと最終PDFを生成する**：同じ確定版からWebブックを一度生成し、採用済みの `src/WebBook.jsx` / `src/web-book.css` を唯一の表示UIとする。QR掲載ONならここで固定URLを確定し、扉直後の入口ページと、選んだ表紙仕様で可能な場合の裏表紙に入れた入稿用PDFを生成する。質問ごとのQRは入れない。QR掲載OFFならQRページを含めず再組版する。WebブックはQR掲載OFFでも本人や許可された家族の作品として生成する。生成中・失敗・完成を注文画面と管理画面に表示し、再試行で重複作品を作らない。
7. **最終校正・入稿・印刷**：運営がPDFとWebの自動検査を見た後、本人が最終紙面とWebブック、表紙・背文字を確認する。QR掲載ONなら最終PDF内のQRを実機で読み、同じWebブックに到達することを確かめる。承認したPDF・版ID・承認日時を記録する。注文条件とPDFのページ数・寸法・背幅・用紙・印刷色が一致するまで入稿できない。印刷会社からの校正も確認してから製造開始を承認する。

「本に仕上げる」では、編集操作と紙面を同じ画面に置く。大きい画面では編集欄の横にページを常時表示し、スマートフォンでは画面内の固定プレビュー領域から現在ページをすぐ確認できるようにする。変更後は該当ページへ自動で焦点を移し、ページ数が変わった場合も示す。PDFの再生成を毎回待つ必要はなく、画面プレビューを即時更新し、ダウンロード操作時にその編集版からPDFを作る。

状態は `編集中（紙面自動更新） → 注文前確認 → 注文処理中 → 注文成立・作品版固定 → Web/PDF生成中 → 最終校正待ち → 入稿可 → 入稿済み → 印刷会社校正待ち → 印刷承認済み → 出荷・実物検品` と分ける。注文成立を入稿可・公開可・印刷承認済みと同義にしない。途中で失敗しても同じ版・同じ公開ID・同じ出力ハッシュで再試行できるようにする。

**順序上の要点**：印刷QRにはWebブックの固定URLが必要だが、Webブックの生成は注文成立後でよい。注文前の紙面ではQR位置をプレースホルダーとして示し、ダウンロードPDFには「QR未確定・入稿不可」と表示する。注文成立後、Webブック生成と固定URLの確定を先に完了し、それを最終PDFへ埋め込む。公開範囲の設定と、外部から実際に閲覧可能にする時点は分け、最終検査が終わるまで外部公開しない。注文後の生成失敗は運営が再試行し、顧客に二重注文を求めない。

## PDFとWebブックの出力仕様

**共通本文**：B5など商品規格を設定値として持つ。扉、Webブック入口、章扉、各語り、写真・キャプション、奥付をテンプレート化し、改ページ・見開き・のど側余白を自動組版する。編集画面の紙面、ダウンロードPDF、入稿PDFは同じページ構造・書体・改ページ規則で描画する。音声はWebで再生し、紙面には語りごとのQRを置かない。動画もWebに置き、紙に載せる静止画は本人確認済みの素材を使う。スタンダードとプレミアムで同じ作品内容を選べば、本文は同じ版を使用する。ただし用紙・製本に合わせた余白やページ構成の違いは、出力設定として明示する。

**スタンダード**：4色の承認済みCMYK値・表紙レイアウトを色マスターとして保持し、可変要素は作品名、著者、表紙写真、裏表紙QRと背幅。色は画面上のHEXだけで固定せず、CMYKと出力プロファイルを含む印刷条件ごとに管理する。注文時に確定した用紙とPP、本文紙、綴じ方、背幅、塗り足しに応じて印刷会社用の表紙4面・背表紙・本文PDFを出す。

**プレミアム**：布色、金箔等の加工、表1と背の文字、見返し、本文紙、綴じ方を商品設定として分ける。布張り金箔なら写真・QRを布表紙へ自動配置しない。今回のサンプルのような箔押し位置見本は製版データと区別する。背幅は最終ページ数と用紙で印刷会社が確定した値を採用し、推計値のまま箔版を確定しない。必要なら会社の校正に合わせて表紙データのみ再生成する。

**Webブック**：紙面のPDF表示ではなく、同じ確定版を文章・写真・音声・動画で見る独立した体験。UI変更でQRのURLを変えない。URLは自社ドメインの `/?voice=<公開ID>` に固定し、Storage直リンクや署名URLを印刷しない。QRを知る人の閲覧と家族の本棚への共有は別の許可として扱う。公開停止・再開は可能にし、元の内容の無断差し替えはしない。

## 自動検査と人による校正

- 作品マニフェストの語り件数・順序・本文ハッシュが、紙PDFとWebブックの収録内容に一致すること。
- メディアIDの対応、音声の再生、写真の読み込み、孤立キャプション、欠けた固有名詞、未確認の素材を検出すること。質問番号やMP3名から対応を推測しない。
- PDFの仕上がり寸法、塗り足し、ページ順、白紙を含む注文ページ数、色空間・出力プロファイル、フォント、画像解像度、総容量、裁ち落とし線・ガイドの残存を検査すること。印刷会社が求める形式の適合性は専用検証と実際の受付結果で確認する。
- PDF内の全QRが一つの正規URLを示し、必要な余白と印刷サイズを保つこと。自動デコードに加え、紙に出力して複数のスマートフォンで実機読取を行うこと。
- 見開きの向き、人物や写真の切れ、余白、キャプションの位置、縦組み・横組みの禁則、背文字の綴りは校正画面と印刷会社校正で人が確認すること。
- 最終出力PDF、制作マニフェスト、公開版ID、QR URL、印刷会社テンプレート版、校正結果、発注番号を一組の制作記録として残すこと。顧客素材と署名URLはログや外部分析へ出さない。

## 負荷・費用・運用上のリスク（2026-10-19時点の試算）

1. **編集のたびに全PDFを再生成すると重い**。ページ組版と写真読込が重複し、スマートフォンのメモリや通信量、サーバー費用を増やす。画面では変更位置から必要な範囲を再組版する。前方の改ページまで連鎖する場合は後続ページも計算し直すが、画面に見えていないページの描画と原寸写真の読込は抑える。画像は表示用の軽い派生画像を使い、正式なPDF生成はダウンロード操作と注文後に限定する。プレビューの更新時間・メモリ・PDF生成時間を実機で測り、長文や大量写真でも画面が固まらないことを受入条件にする。
2. **注文完了後の一括生成は失敗し得る**。現行の公開処理は各音声・写真・動画を順にコピーする。PDF組版まで決済WebhookやSupabase Edge Function一回の中で行うと時間・メモリ制限を越える可能性がある。Webhookは注文成立と耐久的なジョブ登録までにし、素材固定、Web生成、PDF生成、検査、公開を再試行可能な別ジョブへ分ける。各ジョブは注文ID＋作品版で重複実行を防ぐ。自動復旧できないものは管理画面に表示する。
3. **注文中の編集競合**。決済後に現在の `answers` を読み直すと、別端末で変わった文章が注文前校正と違う本になる。注文待ちスナップショットだけを確定対象にし、決済中は編集を一時停止する。キャンセル時は解除し、成立後の訂正は別版と校正履歴で扱う。
4. **保管と配信の費用**。mvp01のローカル素材は写真21点で約12.1 MB、音声17点で約26.1 MB、本文PDFで約13.6 MB。元素材と公開用コピーを両方保持し、PDFも保存すると、動画なしでも概算約90 MB/作品になる。1,000作品で約90 GB、10,000作品で約900 GB。全写真・音声を一度ずつ取得する閲覧を単純計算すると、1,000回で約38 GB、10,000回で約380 GBの配信量になる。これはmvp01を使った規模感であり、実顧客の動画・写真解像度・再生率では大きく変わる。閲覧時は必要な素材だけ取得し、表示用画像を軽量化する。原本と公開版の保管方針、バックアップの容量も計上する。
5. **AI処理費**。現在の文字起こしは `gpt-4o-mini-transcribe`、整文は `gpt-4.1-mini` を使用する。毎回の紙面更新でこれらを呼ばず、録音追加や本人が整文をやり直す時だけ実行する。API使用量は録音時間・入力/出力トークン・再試行回数ごとに記録する。現行文字起こしモデルは2027-02-26終了予定なので、制作基盤の実装と併せて新モデルへの移行検証を進める。
6. **紙とWebの版ずれ**。下書きPDF、確定PDF、印刷会社の校正、Web版のIDとハッシュを記録する。最終PDFのQRは注文後のWeb版が正常に開けることを検査してから入稿する。注文しただけで即座に外部公開・印刷開始としない。

## 軽く動かすための実装方針

費用の厳密な事前見積りは実装の前提にしない。まずは**編集1回につきサーバー上のPDF生成・画像複製・AI呼び出しを0回**にする。プレビュー、保存、PDF取得、注文後制作を別の処理として設計し、実測してから必要な部分だけ最適化する。

| 契機 | 行う処理 | この契機では行わない処理 |
| --- | --- | --- |
| 語り・写真・順序などの編集 | 画面の状態をすぐ更新し、短い待機の後に組版結果を更新。保存は変更をまとめて送る | PDF書き出し、Webブック生成、AI整文、原寸画像の全件取得 |
| 紙面を閲覧 | 必要なページだけ描画し、写真は表示用の軽量版を読む | 全ページの画像DOM生成、印刷用画像の取得 |
| 下書きPDFボタン | その瞬間の版番号と内容を固定し、共通ページ構造から一度だけ書き出す。同一版・同一出力設定なら完成済みPDFを再利用 | Webブック生成、作品の注文確定 |
| 注文開始 | 本人が承認した版のスナップショットを保存し、決済中の編集競合を止める | Webブック公開、最終PDF作成 |
| サーバーが注文成立を確認 | 同一注文・同一版について制作ジョブを一つ登録 | 決済応答の中で大量の媒体コピーやPDF組版を完走させる |
| 制作ジョブ | 素材固定→Webブック生成→QRの固定URL確認→最終PDF→自動検査の順に処理し、各段階の結果を保存 | 成功済み段階の無条件再実行、本人に二重注文を求めること |

**組版の分担**：文章・写真・キャプションから「ページ構造と改ページ」を決める部分を単一の純粋な処理として実装する。画面とPDFはその構造を別々に描画するが、ページ数・掲載内容・写真位置の決定を重複実装しない。最初から複雑な差分組版を作る必要はない。初版では変更を短時間まとめてWeb Worker等で全体のページ構造を再計算し、画面には見えているページだけを描く。実機で再計算が遅いと分かった場合に、変更箇所から後続ページまでの差分計算を追加する。文字・画像の読み込み条件が変わってもページ落ちや文章の切断で「速く見せる」ことはしない。保存完了を待たずに画面を更新してよいが、注文とPDFの入力は確定した版番号に紐付ける。

**画像と媒体**：プレビューはサムネイル、Webは表示サイズに適した派生画像、入稿PDFは印刷用原本を使う。音声・動画は紙面閲覧で事前取得しない。公開時のコピーは素材ハッシュで管理し、同じ作品版の再試行で重複させない。動画は自動再生せず、容量と転送量を写真・音声と分けて計測する。署名URLを永久保存するのではなく素材IDから必要時に発行する。

**注文処理**：決済Webhookは検証済みイベントを記録してジョブを登録したら速やかに返す。ジョブは注文ID＋作品版＋工程名を一意キーにし、状態・試行回数・最終エラーを保存する。時間制限を越える媒体処理は小分けにし、途中から再開可能にする。Webブックの入口URLは再試行でも変えず、外部公開と印刷入稿は自動検査・最終校正の通過後に行う。失敗は管理者に見え、支払い済み注文を失わないことを優先する。

**費用と性能の判断線**：試作時に、典型的な92ページ相当と長文・写真が多いケースで、操作後のプレビュー更新時間、スマホの使用メモリ、下書き/最終PDFの生成時間、1作品の保存量、1回の閲覧で実際に転送した量を記録する。値が悪い箇所にだけサムネイル、ページ仮想化、組版キャッシュ、媒体形式の見直しを追加する。月額費用は当面、作品数・保存GB・配信GB・生成ジョブ回数・AI利用量の5項目で追い、一定量を超えたら通知する。高コストな動画や大量再試行は注文単位で上限と運営確認を設ける。

**最初の実装単位**：現行 `BookPagePreview` の10段落打切りと固定枠のはみ出しを解消するため、まず一つの語りから全文を失わず複数ページへ分けるページ構造を作る。その構造を画面のプレビューに出し、同じ入力を下書きPDFに書き出してページ数・掲載内容を照合する。そこまで完了してから、注文成立後ジョブへの接続とWebブックの確定処理を変更する。現行の注文前 `confirm_book_work` / `prepare` だけを先に外すと、支払い済み注文の制作が途切れるため、代替ジョブが完成するまで既存経路を切り替えない。
